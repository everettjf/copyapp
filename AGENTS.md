# Copy APP agent entry

This repository implements two user-facing jobs on jailbroken iPhones:

1. **Analyze an installed app.** Identify the exact USB device and Bundle ID, collect the app package, UI and sandbox evidence, decrypt encrypted Mach-O files when the verified device path supports it, inspect selected functions, run targeted UI/Frida experiments, and deliver a cited deep report plus `feature-spec.json`.
2. **Rebuild selected behavior.** Use that specification to create an independent, runnable iOS app, install and launch it on the requested real devices, compare the same flows, and report verified coverage and remaining differences.

Treat a request such as “分析这个 App” or “Copy this app” as authorization to carry out the corresponding job. Work from the connected device and current files; only request missing device/target details when they cannot be discovered. Do not stop after `copyapp analyze`: its `analysis.md` is a collection index. Complete the function interpretation and `copyapp report` step described in `skills/copyapp-analyze/SKILL.md`. For the rebuild phase, follow `skills/copyapp-rebuild/SKILL.md`. For an initial device inventory, follow `skills/copyapp-survey/SKILL.md`.

For each representative UI flow, prefer one `copyapp flow-capture` case when the final screen needs structural analysis. It runs the bounded playbook and captures the resulting UIKit/accessibility view without launching the App again. Keep original and rebuilt runs separate, then use `copyapp compare-playbooks` on their child `playbook/` directories. Cite the composite case in the report so the screenshot and view tree share one verified device, App, backend, and short observation window.
When a flow also needs runtime code evidence, pass one or more `--method 'ClassName::selector:'` arguments to `flow-capture`; add `--binary` and its matching `--objc-index` to hook the acquired App's original entry as well as the current Objective-C IMP. The trace child records counts for each tap step and preserves the exact hook source. Treat those counts as temporal observations, and validate the imported composite case against the original binary hash.
Pass a completed traced flow to `copyapp candidates --flow` for step attributed static method addresses. By default, `copyapp native-queue` records bounded ARM64 assembly for candidate entries and follows only unique local direct call/branch targets; inspect its stops before writing functional conclusions. When an REA provider is available and explicitly selected, `copyapp rea-queue` and `copyapp rea-bridge` add decompiled function evidence. None of these queues alone generates a semantic interpretation.
For pseudocode without REA, use `--provider ghidra-direct --ghidra-dir <GHIDRA_INSTALL_DIR> --java-home <JDK_HOME>` with `investigate-flow`, `investigate-app`, `prepare-analysis`, or `prepare-app`. It ranks verified runtime/static candidates, follows unique direct local calls from the validated native queue, runs Copy APP's packaged Ghidra script, and includes pseudocode with each function's origin in the agent review task. The entry function limit does not include those bounded native followers. For an existing candidate case, use `copyapp ghidra-queue` and pass `--native <NATIVE_QUEUE>` when available; for one explicitly chosen address, use `copyapp ghidra-function`. If a large binary times out, use `--ghidra-disable-analyzer 'Objective-C Message Analyzer'` on the investigation/preparation commands, or `--disable-analyzer` on the standalone commands, then review the recorded analysis profile. A timed-out Ghidra import is rejected even if its post-script wrote pseudocode. These paths require external Ghidra/JDK but no REA CLI. Import the result into `copyapp report` with `--evidence`; verify the binary hash and address chain before interpreting it. The default provider remains `none` to avoid spending decompiler time unless requested or useful for the task.
When a direct local call chain stops at an indirect `blr`, use `copyapp ghidra-indirect --udid <UDID> --investigation <CASE> --objc-index <INDEX> --ghidra-dir <DIR> --java-home <DIR> --out <NEW_CASE>` to discover bounded sites from the verified native queue, replay the saved playbook with register capture, and decompile observed app-image callbacks. Its `queue/` child can be imported by `copyapp report`. For an explicitly selected site, `flow-capture` followed by `ghidra-queue --branch-flow <FLOW_CAPTURE> --native <NATIVE_QUEUE>` remains available. Review the same-step runtime hit and instruction binding. A temporal hit identifies code executed in the observation window; it does not by itself prove that the callback caused the visible UI change.
If `ghidra-indirect` saved a complete branch replay but Ghidra failed, use the same arguments and output with `--resume`. It verifies and reuses the phone trace and archives the failed Ghidra queue. If the phone replay itself failed, start a new case after reviewing App state; do not assume an interrupted tap is safe to repeat.
For a verified `analyze` case and one bounded playbook, `copyapp investigate-flow` runs method scouting and UI capture, plus trace and candidate binding when a method is selected. Direct Ghidra is available with `--provider ghidra-direct`; the legacy REA bridge remains available only with explicit `--provider ghidra|hopper`. By default, available static candidates also receive bounded ARM64 disassembly from Xcode llvm-objdump; missing Xcode records unavailable assembly and does not block the UI/Frida investigation. Read its `review-brief.md` and all linked raw evidence, then write the deep findings and feature specification; in the default no-REA mode, ambiguous method scouting still collects UI evidence and marks method tracing as unavailable; explicit legacy REA runs can stop at `needs_review` for a method selection and continue with `--resume --method`. Resume also reuses verified complete stages after a later failure. The previous scout is retained when a reviewed method is chosen.
For a default no-REA flow with a labelled tap and ambiguous static scout, the investigator first captures an entry UIKit tree and may select the unique action method on the visible button's runtime class. A failed or ambiguous entry scan falls back to UI-only evidence. Treat this as candidate selection; inspect the later Frida trace for actual method hits before making code claims. The XR DeepSeek automatic selection case is `cases/deepseek-no-rea-auto-method-investigation-20261015`.
For several selected flows in one app, run `copyapp investigate-app` with repeated `--script`; it saves one verifiable parent case and resumes without repeating completed flows. `copyapp report --evidence ID=<APP_INVESTIGATION_DIR>` can import the complete set.
After `copyapp draft-analysis`, follow its `TASK.md` to review each linked UI, trace, native assembly and optional decompiler artifact, then produce supported findings, a concrete feature specification and a separately verified deep report. The generated task and fact draft only establish input readiness.
For a verified `analyze` case and selected playbooks, `copyapp prepare-analysis --udid <UDID> --analysis <CASE> --script <PLAYBOOK> ... --out <CASE>` joins `investigate-app` and `draft-analysis` behind one resumable entry. Read `<CASE>/draft/TASK.md` after its status becomes `needs_semantic_review`; this is a handoff to the current coding agent, not a finished deep report. Use `--resume` after a failed investigation. It archives a verified failed flow capture under `attempts/` before retrying that flow and reuses complete flows without another device run. Existing complete investigations may be supplied with `--investigation` to regenerate the handoff without touching the device.
For a specific database in the indexed app data container, use `copyapp sandbox-file` against a verified analysis case, then `copyapp sqlite-schema` on the saved file and cite only the structure case in the report. The raw file stays in ignored local `cases/`; copying live SQLite and WAL files sequentially is not an atomic database snapshot.
For a captured preference plist, use `copyapp plist-schema` and cite its verified key/type structure. Its report omits values; the raw captured plist may contain private data and remains local.
When the analysis case does not yet exist and selected original App playbooks are ready, use `copyapp prepare-app --udid <UDID> --bundle <BUNDLE_ID> --script <PLAYBOOK> ... --out <CASE>`. It requires no REA by default, preflights it only for an explicit provider, then joins `analyze` and `prepare-analysis`; `--decrypt` requests full-package recovery for an encrypted App. On success, review `<CASE>/preparation/draft/TASK.md` and continue to a sourced deep report. The parent case and its children must pass `copyapp verify`; `--resume` reuses complete source-verified stages without repeating device work.
For a report produced from that task, retain `source_script_sha256` on each reviewed specification flow and run `copyapp analysis-delivery --task <DRAFT> --report <REPORT> --out <DELIVERY>`. It checks flow coverage and source identity; inspect the underlying function reasoning yourself because hashes do not prove semantic correctness.
`copyapp report --evidence ID=<INVESTIGATION_DIR>` validates and imports that complete case, including its flow, candidate, available native assembly and optional REA source chain. Cite the composite ID for conclusions that join these stages.
Before implementing a rebuild from a verified deep report, run `copyapp rebuild-plan --report <REPORT_CASE> --out <PLAN_CASE>` to derive cited original/clone playbook pairs. Inspect any flow marked missing or ambiguous; the generated clone scripts change only the Bundle ID and do not implement the app. Once the independent app launches, use the plan's `rebuild-check` inputs for same-device validation.
Generate `copyapp agent-task --report <REPORT_CASE> --plan <PLAN_CASE> --udid <UDID> --project <SOURCE_DIR> --out <TASK_CASE>` and use its verified `TASK.md` as the evidence-linked coding brief. Treat `ready_for_agent` as input readiness only. Continue through source implementation, package/build, real-device installation and `rebuild-check`; retain any remaining visual or behavioral gaps in the final report.
For a single resumable handoff, use `copyapp prepare-rebuild --report <REPORT_CASE> --udid <UDID> --project <SOURCE_DIR> --out <PREPARATION_CASE>`; select a subset with repeated `--flow` and resume the same source and settings with `--resume`. It writes `plan/` and `task/TASK.md`, verifies source identity, and retains damaged child attempts. A task marked `needs_evidence` requires original UI evidence before implementation.
After installing a clone, `copyapp rebuild-task-check --task <TASK_CASE> --out <REBUILD_CHECK_CASE>` runs the verified task's selected pairs on its pinned device, without copying the generated long comparison command. Supply `--udid` only if the task left the device open; use `--resume` to continue an interrupted check. Inspect the finished case and its saved screenshots.
When only selected report flows are requested, `agent-task` uses `selected_flows_ready` and records the omitted flow IDs. `agent-run` accepts that reviewed selection and prompts the coding agent to disclose the omitted scope. `agent-delivery` may cite a device check containing additional flows, but counts and reports only those selected in the task; it lists the extra checked and omitted flows separately.
When already operating inside Codex or Claude Code, carry out the analysis or rebuild task yourself. The optional `copyapp agent-run` command launches one of those CLIs from a standalone shell and records its process output; avoid nested agent launches from an active coding-agent session. A successful agent process exit is not proof of a deep report or rebuilt App.
For a standalone semantic-review run, use `agent-run --verify-analysis` to require the agent's formal report at `<RUN>/reviewed-report` and automatically create a source-linked `<RUN>/analysis-delivery` case. Inspect that verified delivery and its findings; a passing source check still cannot certify function semantics. This option does not apply to implementation tasks.
For a standalone implementation run, `agent-run --verify-rebuild` fixes the install, rebuild-check, visual-review and final-delivery paths under `<RUN>`. It returns success only after a verified delivery has behavior assertions for every selected flow, complete screenshot review and no major visual difference. Minor differences remain recorded. Do not launch a nested Agent from an active Agent session; implement and verify the same steps directly.
After building, installing and checking the App, create `copyapp agent-delivery --task <TASK_CASE> --install <INSTALL_CASE>/install.json --check <REBUILD_CHECK_CASE> --out <DELIVERY_CASE>`. It binds the source tree and installed IPA to exact device, build and selected flow evidence. Its scope and visual-review fields, not the Agent CLI exit code, determine what has actually been verified.
Inspect every saved screenshot pair and record explicit judgments with `copyapp visual-review --check <REBUILD_CHECK_CASE> --judgments <JSON> --reviewer <NAME> --out <VISUAL_REVIEW_CASE>`. Pass that case to `agent-delivery --visual-review <VISUAL_REVIEW_CASE>`. Record visible differences, even if pixel metrics pass. The reviewer label is self-declared; the verifier establishes image identity and review coverage, not the truth of the subjective judgment.

Use `.venv/bin/copyapp` from the repository root. Specify `--udid` and `--bundle` for device operations. Keep screenshots, extracted App data, IPA snapshots, traces, and device credentials in ignored local `cases/`; report files may link to those local cases. Run `copyapp verify` on every collected or composed case. A matching hash proves file consistency, not the correctness of an interpretation. Preserve failed and partial evidence; mark claims as observed, inferred or unknown. REA pseudocode is generated by a decompiler, not original source.

Do not claim iOS 17 or iOS 26 compatibility from XR evidence. The current pilots are Compass and Calculator on iPhone XR iOS 16.1.1; the known-source fixture and its independent FixtureClone exercise three SwiftUI/UIKit/data flows on the same XR. The fixture's third XR comparison aligned existing visible counts through clone UI actions; its five screenshot pairs retain minor system-chrome differences, and SQLite row contents remain unverified. The user has deferred tests on the other two phones for now. See `PLAN.md` for acceptance criteria and `README.md` for commands and tool status.
