# iCTRL runner on iPhone XR: paired device trial

## Internal identifier update (2026-10-16)

The vendored source now uses `com.copyapp.ictrl` for URL registration names, pairing-file UTI and dispatch queue labels, and `com.copyapp.ictrl.auth` for the legacy Keychain service. The URL schemes `ictrl` and `ictrl-app` and the RPC protocol did not change. The optional settings app was rebuilt but not installed on the XR.

Xcode 27 built and signed the iOS 16 runner IPA (SHA-256 `8bb97b9d780639cc837f3106be6e6ba0e190908dec25a83606c03e08bdfc0b89`). `copyapp setup ictrl --reinstall` installed it under the existing `com.copyapp.ypv49m8592.ictrl.uitests.xctrunner` Bundle ID, stopped the previous process, launched the runner, and passed an authenticated call without another pairing approval. The case is `cases/ictrl-internal-rebrand-20261016/setup/` and passes `copyapp verify`. The installed XCTest binary contains `com.copyapp.ictrl.auth`, read back over authenticated USB SSH. Its whole-file hash differs from the archived XCTest binary, so the string check and the install/launch evidence are the basis for the on-device version claim rather than byte-for-byte binary identity. Current sessions survived because iCTRL stores them in its sandbox `TokenFileStore`; only sessions existing solely under the old legacy Keychain service would need a new pairing.

## Integrated Copy APP setup (2026-10-16)

### Bundle ID migration to `com.copyapp`

The vendored signing default now generates `com.copyapp.<lowercase-team-id>` instead of the upstream prefix. The ignored local signing file on this Mac was updated to `com.copyapp.ypv49m8592`. Xcode 27 built and signed `com.copyapp.ypv49m8592.ictrl.uitests.xctrunner` for iOS 16.0; the IPA SHA-256 is `6be8fc281ca5b3cc5b8294c7abadb780b8f5bac4103e4db4f4877bf16124a396`. Strict deep signature verification passed.

On the XR, Copy APP installed the new Bundle ID through TrollStore, stopped the previous runner, and recorded the new ID for that UDID (`cases/ictrl-copyapp-bundle-20261016/setup/`). The first launch hit iOS's notification permission prompt and timed out; permission was granted through the existing iOS MCP UI channel. The next pairing request appeared on the unlocked phone with the same eight-character fingerprint shown by the Mac client, and its **Allow** action was selected through that channel. `setup` then passed authenticated health (`cases/ictrl-copyapp-bundle-20261016/ready/`). After confirming both app identities, the old upstream-namespaced runner was uninstalled. A final setup check (`cases/ictrl-copyapp-bundle-20261016/after-cleanup/`) passed with only the `com.copyapp` runner installed. Other iOS versions were not tested.

Copy APP now carries the Apache-2.0 iCTRL source snapshot at `vendor/ictrl/` (revision `d88bbf0b3a5addead31b4298d605d7ac7a87d6e7`) and exposes `copyapp setup ictrl --udid <UDID> --out <CASE>`. It builds and self-tests the Mac CLI, detects the exact USB device and its iOS version, builds the signed runner if absent, installs through the existing TrollStore/SSH path, starts a temporary USB forward, pairs when needed, and requires an authenticated `logs` call. The pairing token remains in the upstream client's local store. The `setup` case records stage status and hashes; `copyapp verify` checks its local evidence.

The vendored source built successfully with Xcode 27 on this Mac. `COPYAPP_IOS_TARGET=16.0 make ipa` inserted the upstream XCTest shim, changed the **outer** XCTRunner Mach-O and Info.plist minimum from 17.0 to 16.0 before upstream's inside-out signing, and produced the original upstream-namespaced runner with IPA SHA-256 `c38dec36bb5927479448c49c9c0e6205beae68bb53b88f6f9a9cd69e0057fb7b`. `codesign --verify --deep --strict` passed outside the filesystem sandbox. The cached pinned IDevice framework and pre-existing local signing configuration were reused for this build; a clean download/signing setup was not retested.

On the XR/iOS 16.1.1, `setup` first reused the installed runner and existing pairing (`cases/ictrl-setup-xr-20261016/`). A second run with `--runner-ipa vendor/ictrl/iCTRLUITests-Runner.ipa --reinstall` installed the then-current vendored build via TrollStore, confirmed package version/build and the staged hash, reached the runner over USB and passed authenticated health (`cases/ictrl-setup-reinstall-xr-20261016/`). Both setup cases passed `copyapp verify`. A subsequent doctor case (`cases/ictrl-doctor-after-setup-20261016/`) reported `ictrl: available`; its `ssh_mobile` row was unavailable because the persistent SSH forward had been closed after setup, while the install itself had verified SSH identity. The later `com.copyapp` migration above exercised a new runner identity and phone-approved pairing. These XR setup cases did not test iOS 17; a later [iPhone 14 validation](relaxin-roothide-iphone14.md) did. iOS 26 remains untested.

Device: iPhone XR (`<XR_UDID>`), iOS 16.1.1, Dopamine rootless. Trial on 2026-10-15. The upstream checkout is `OpenMinis/iCTRL@d88bbf0b3a5addead31b4298d605d7ac7a87d6e7`; the Mac client from that revision passed its local crypto self-test earlier.

## Build and installation

The upstream source was copied to `/private/tmp/copyapp-ictrl-build-20261015/` and `make ipa` succeeded under Xcode 27. It fetched `idevice v0.1.68`, built the host app and `iCTRLUITests-Runner`, inserted the upstream iOS 16 XCTest compatibility shim, aligned the nested `.xctest` Bundle ID, signed the nested shim/test bundle and runner, and verified the code signatures. Build output stayed outside the Copy APP repository.

Xcode 27's prebuilt runner executable and outer `Info.plist` declared minimum iOS 17.0 even though the project and nested `.xctest` target iOS 16.0. In a **separate test copy**, `vtool` changed only the outer runner's `LC_BUILD_VERSION` minimum to 16.0, the outer `Info.plist` minimum was set to 16.0, and the shim, `.xctest` and runner were signed inside out again. `codesign --verify --deep --strict` passed. The test IPA SHA-256 is `0c62a4789c554576b43a84945698a4c47af53dc731e0ef19a7bc5e91b7a45213`; it is local at `cases/ictrl-runner-compat-20261015/iCTRLUITests-Runner-ios16.ipa`. This adjustment is a local compatibility experiment, not an upstream-supported Xcode 27 build configuration.

`copyapp install` transferred the IPA via the exact XR UDID, matched the staged hash, invoked TrollStore's helper, and confirmed the original upstream-namespaced runner with InstallationProxy. The result is `cases/ictrl-runner-xr-install-20261015/install.json`. The XR has a Developer Disk Image mounted at `/Developer`. iOS MCP launched the runner; a notification authorization prompt appeared, and the existing UI channel tapped **Allow**. After that, the runner posted **iCTRL Server Ready** and a USB port forward to device port 8200 returned `/whoami` with protocol version 1 and server version 1.98.12. Thus launch and server availability are observed, beyond installation alone.

## Pairing and UI validation

The Mac client's `/pair` request displayed a fingerprint, and an XR notification displayed the matching fingerprint. After an initial incomplete attempt and the upstream pending/cooldown window, the one-off helper at `cases/ictrl-runner-compat-20261015/pair_once.py` matched those fingerprints, opened the notification action list through the existing iOS MCP touch channel, selected **✅ Allow**, and the Mac client returned `paired`. The token remains only in the upstream client's local user store; it is not included in this repository or report.

Authenticated `copyapp ui health --backend ictrl --port 22224` succeeded. The same channel read the SpringBoard and Compass accessibility trees, launched `com.apple.compass`, captured a native 828×1792 screenshot, and tapped the original Compass dial at `(207,325)`. Before and after screenshots at `cases/ictrl-xr-compass-20261015/before.jpg` and `after.jpg` visibly show the bearing-lock marker appearing at 135°. An independent iOS MCP screenshot of the same initial screen is `ios-mcp-before.jpg` (414×896); the resolutions differ, so the two sources remain separate evidence. Compass's custom-drawn dial has sparse accessibility coverage; screenshots or OCR are needed for its full content.

This verifies pairing, encrypted RPC, foreground launch, page source, screenshot and touch on this XR. This XR trial did not test other iOS versions; a later [iPhone 14 / iOS 17.3.1 trial](relaxin-roothide-iphone14.md) verified paired Calculator UI flows. iOS 26 remains untested.

The upstream `screen_text` method also returned OCR results on the Compass screen (20 entries, local evidence `cases/ictrl-xr-compass-20261015/ictrl-ocr.json`). It includes screen positions, but some degree glyphs and punctuation were misread, so reports should retain the screenshot beside the OCR. After two crashes in the separate iOS MCP Vision path, the iCTRL runner was no longer reachable through its old tunnel; its OCR result predates those crashes. The paired USB screenshot and Mac Vision fallback is documented in [XR OCR validation](xr-ocr-validation.md).

The one-command `copyapp experiment` path now supports both UI backends while using the same Frida trace code and point-space tap coordinates. On the original `com.apple.compass`, the iCTRL run `cases/experiment-ictrl-original-bearing-20261015/` launched the app, verified its foreground Bundle ID, captured native-resolution before/after JPEGs, tapped `(207,325)`, and recorded `CompassView::tappedCompass:` once. A second run `cases/experiment-ictrl-private-tunnel-20261015/` omitted `--port`; it automatically launched the paired runner and established a temporary named-device USB forward, then completed with one call. The matching iOS MCP run `cases/experiment-ios-mcp-after-ui-adapter-20261015/` also completed with one call. The reporter's experiment validator accepted the iCTRL case with the same device and app identity as the Compass base case. The post-tap iCTRL screenshot displayed the bearing-lock marker; some location text was absent in that later device state, so this is evidence for the lock interaction, not a full screen-equivalence claim.
