# XR OCR validation, 2026-10-15

The test device is the paired iPhone XR on iOS 16.1.1 with Dopamine rootless. OCR is evidence for visible text, not proof of an App's implementation or a safe tap target. Original screenshots and JSON are retained in local, Git-ignored case directories because the Compass screen contains location data.

## Device OCR failure

The iOS MCP tweak's `ocr_screen` using Apple's Vision framework crashed SpringBoard twice. The first crash is `cases/ictrl-xr-compass-20261015/ios-mcp-ocr-springboard-crash.ips`; after setting `VNRecognizeTextRequest.usesCPUOnly = YES`, the second crash is `cases/ios-mcp-ocr-fix-20261015/springboard-crash-after-cpu-only.ips`. Both reports show `SIGTRAP` from a libdispatch semaphore in Vision's detector path with ANE frames. CPU-only did not prevent the failure.

Package `com.copyapp.mcp` version `0.1.2-1+debug` was installed through the existing USB root bridge. It returns an error before constructing a Vision request when hosted by SpringBoard. The Mac adapter also rejects direct `ocr_screen` and `describe_screen(include_ocr=true)` before any RPC. After the second crash and package reload, SpringBoard remained alive and Compass could launch, but ElleKit had not injected `copyapp-mcp.dylib`; the 8090 service was unavailable.

Inspection of the installed ElleKit `MobileSafety.dylib` revealed its `/var/mobile/.eksafemode` marker. The device marker recorded a SpringBoard signal 5 crash at 09:06; a local copy is `cases/ios-mcp-ocr-fix-20261015/ellekit-safe-mode-marker.txt`. After preserving it, the marker was removed. `sbreload` alone did not restore injection. A standard `ldrestart` through `copyapp root-run` did: Frida then listed the installed `copyapp-mcp.dylib` in SpringBoard, and `/health` returned version 0.1.2. One direct `ocr_screen(engine=vision)` integration probe returned a controlled `isError` with the disabled message; SpringBoard PID remained 6377 and `/health` still succeeded. Evidence: `cases/ios-mcp-ocr-fix-20261015/guard-live-result.json`. Both iOS MCP and iCTRL health checks subsequently passed.

The final 0.1.3 package removes `ocr_screen` from the advertised and accepted UI tools. `describe_screen(include_ocr=true)` now returns a controlled error before reaching any OCR engine. Its archive contained only the tweak, filter plist and license notices; transferred and device hashes matched. After installation, `sbreload` alone again left the tweak unloaded with no Safe Mode marker, while `ldrestart` restored injection. Live checks returned `/health` version 0.1.3, no advertised device OCR tool, a `-32601` rejection for direct `ocr_screen`, and a controlled error for `describe_screen(include_ocr=true)`. SpringBoard PID stayed 6497. This distinction matters: an unloaded tweak after `sbreload` is not by itself evidence of another crash or Safe Mode entry.

## Working host routes

- iCTRL `screen_text` returned 20 OCR entries from the original Compass screen, saved at `cases/ictrl-xr-compass-20261015/ictrl-ocr.json`; some characters were misread.
- `copyapp ui ocr --backend usb --udid <XR_UDID> --out cases/ios-mcp-ocr-fix-20261015/compass-usb.png` captured the live 828×1792 screen using Apple's USB screenshot service, then ran a short-lived macOS Vision process. It returned 22 text entries in `compass-usb-ocr.json`, including heading digits and compass cardinal labels. It did not call the iOS MCP tweak. The JSON retains the screenshot SHA-256 and pixel coordinates.
- The iOS MCP adapter runs the same Mac OCR process on its screenshot result, then checks screen point dimensions before marking tap-coordinate mapping verified. On the settled Compass screen it returned 20 text entries, image 414×896, `point_mapping_verified=true`, and `coordinate_space=fixed_screen_points`. The screenshot and result are `cases/ios-mcp-ocr-fix-20261015/compass-ios-mcp-settled.jpg` and `compass-ios-mcp-settled-ocr.json`. An immediate capture during the launch animation had only two entries, so an agent must wait for a stable screen or compare successive observations before treating OCR as a page description. iCTRL's recovered channel returned 19 entries in `compass-ictrl-ocr.json`.
- The 0.1.3 Mac client now compares successive downscaled screenshots before OCR and records `capture_stability`, foreground Bundle ID before/after, screen power/lock readiness and point mapping. On the live XR Compass page, it found a stable frame in two samples, 20 OCR entries, both foreground IDs `com.apple.compass`, screen ready and verified fixed-point mapping. Evidence: `cases/ios-mcp-ocr-fix-20261015/compass-ios-mcp-0.1.3-stable-ocr.json`. Visual stability is a short-window observation, not a guarantee of semantic page readiness.

The OCR text and boxes require visual review; neither backend guarantees accurate reading of custom-drawn text. The USB route's coordinates are screenshot pixels and must not be passed directly as iOS MCP point coordinates.
