## Build and interaction path

The latest local IPA SHA-256 is `f2537ef2a5edbbe25d598c286841d34c16087883e9e43e1704b9c0fdd1ce5d1a`. `copyapp install` matched the staged file on the XR, invoked TrollStore's local helper and confirmed `dev.copyapp.compass` through InstallationProxy (`cases/compass-location-layout-install-20261015/install.json`). TrollStore may change the installed executable bytes during signing, so its on-device binary SHA-256 is not compared directly with the preinstall IPA binary.

REA/Ghidra inspection of the acquired original binary shows `CompassPageViewController::updateDisplay:` reads `deviceMotion.heading`, and `startMotionManager` selects the magnetic north reference frame when `_usesTrueNorth` is false. A read-only Frida probe on the XR found `_usesTrueNorth=0` in that run (`cases/compass-motion-frame-20261015/result.json`). The first rebuild used the true north frame and showed 149° near an original 136° capture. After switching to magnetic north, near-time captures showed original 136° and rebuild 137° (`cases/compass-magnetic-original-unlocked-20261015.jpg`, `cases/compass-magnetic-clone-20261015.jpg`). This is a point-in-time comparison, not a calibrated accuracy test. The rebuild now polls CoreMotion at up to 60 Hz, with CoreLocation heading as an availability fallback.

The original `_openMaps` implementation embeds `maps:ll=%f,%f&trackingMode=2`; the rebuild uses the same URL format. A Frida and UI experiment on the latest IPA recorded one `openMaps` call and Apple Maps in the foreground. Frida unload/detach timed out after the handoff, but the complete observation was saved first. The experiment runner now streams hook hits to the Mac, so it does not wait on a synchronous Frida RPC after the target moves to the background.

The XR's rootless `com.copyapp.mcp` package was installed through Filza's local DEB view and `sbreload` restarted SpringBoard. Through a USB port forward, the service identified itself as `copyapp-ios-mcp` and returned a real 414×896 JPEG screenshot. Its first screenshot was black because the display was off; `wake_and_home` then produced a visible Home screen capture. `copyapp ui launch`, `observe`, `screenshot` and `tap` all worked on the XR. The USB Accessibility Audit `press` API had earlier returned an activation request without changing the screen; it is not the validated touch path.

## Remaining differences and limits

Font weight, tick rendering, dial motion, bearing-marker placement and some spacing still differ. The screenshots do not establish pixel-level parity. The Frida counters establish calls within the observation window, not their order or arguments. Only sandbox metadata was collected; file contents and network behavior remain unverified. The iOS 17 and iOS 26 phones have not been connected for this test.

## Repeatable bearing comparison

`copyapp playbook` now accepts a scenario ID and an optional stable screenshot gate. The Compass scripts at `rebuild/CompassClone/playbooks/bearing-original.json` and `bearing-rebuilt.json` fresh-launch each app, capture an unlocked screen, tap the same screen point twice, and capture the locked/unlocked states. Each screenshot requires the target app to remain frontmost, a settled image and visible heading content. The runs are paired by `copyapp compare-playbooks`, which checks device, UI backend, action sequence, tap coordinates and the SHA-256 of source evidence.

The first paired attempt (`cases/compass-bearing-comparison-20261015/`) caught a launch-transition frame in its first screenshot, even though both playbooks returned `complete`. It remains as a diagnostic and is not acceptance evidence. The later checked run is `cases/compass-bearing-comparison-checked-20261015/`; its report and 23 recorded artifacts passed `copyapp verify`. Both apps were captured on the same XR with iOS MCP at 414×896. The configured red-marker region had pixel counts **0→134→0** for Compass and **0→58→0** for Copy Compass, before/after the first tap and after the second. Both satisfied the specified rise-and-return check. The three full-frame mean absolute RGB differences were approximately 0.0255, 0.0253 and 0.0250; these are descriptive only because time, sensor and location values differ between runs. The red marker's area and shape still differ visibly, and the check does not validate every bearing angle or animation frame.

The same paired-script path now covers the location-to-Maps flow. `maps-original.json` and `maps-rebuilt.json` both captured a settled Compass screen, tapped `(207,712)`, then waited for `com.apple.Maps` to become frontmost. On the XR, both completed; the original reached Maps on the first check and the rebuild on the third. The paired report at `cases/compass-maps-comparison-20261015/report.md` passed `copyapp verify`. It verifies app handoff, while the actual Maps pin/coordinate and location-denied state remain unverified.

Hopper and Ghidra independently decompiled `CompassBearingView::layoutSubviews` at `0x100001e48` from the same acquired Compass binary. Both expose an inner arc, a line to the outer radius, a returning outer arc and a `CGPath` assignment to `_bearingDeviationLayer` when the locked bearing differs from the current angle. The rebuild now draws a filled annular sector for a nonzero difference. The newly installed IPA passed the paired XR bearing playbook; `cases/compass-bearing-sector-comparison-20261015/report.md` and its source artifacts passed `copyapp verify`. Red-marker counts were 0→146→0 for the original and 0→57→0 for the rebuild. The phone remained nearly stationary during this run, so it did not exercise a visibly wide sector; its geometry and rotation response are still unverified. The source-level inference is included in the verified `cases/compass-xr-deep-report-v9-20261015/`.

The stationary-state limitation was addressed with a controlled 45° in-memory experiment on each app. On the original, Frida temporarily changed `CompassBearingView._angle` and requested `updateLayer`; on the clone it offset `CMDeviceMotion.heading`. Both hooks were removed, and the original view angle and visible red area returned to their starting values. The original runtime view had 82 pt and 119 pt inner/outer radii. Ghidra showed that its shape layer uses `UIColor.redColor`. The clone now scales those radii from the XR dial size, draws the sector above cardinal labels and uses `UIColor.red`.

The retained [sector comparison](../cases/compass-offset-comparison-v2-20261015/report.md) and its source cases passed `copyapp verify`. In the 100×80 px sector region, the original had 2890 red pixels, the clone 2900; their red masks overlapped with intersection over union **0.95344**, and their dominant quantized RGB bins both measured `(230, 50, 30)`. This validates one rendered 45° sector on the XR. Because the injection points differ, the whole-screen heading and dial rotation differ during this experiment; a real physical rotation, animation timing and behavior on other devices remain unverified. The original-side findings are included in the verified `cases/compass-xr-deep-report-v10-20261015/`.

The coordinate tap was also replayed with a Frida hook on `UIApplication` URL opening. Both apps emitted one `maps:ll=…&trackingMode=2` request with **identical URL bytes** and then showed Apple Maps in the foreground. After waiting for the transition, both screenshots showed the same local map view and blue location dot. The [Maps URL comparison](../cases/compass-maps-url-comparison-v2-20261015/report.md), its two source cases and the original-side findings in `cases/compass-xr-deep-report-v11-20261015/` passed hash verification. Exact coordinates remain in ignored local evidence. This verifies the request and observed destination for the current authorized location; permission-denied and other locations remain untested.

Static Ghidra evidence for the original `locationManagerDidChangeAuthorization:`, `startLocationUpdatesIfNecessary`, `setUserLocation:`, `_shouldHideCoordinateLabel`, `_updateCoordinateLabel` and `_updatePlaceLabels` traces the denied/restricted branch to stopped updates, a nil user location, hidden coordinates/elevation and cleared place text. The rebuild's empty-location UI now hides those fields instead of showing a permission message. Its updated IPA was installed, and the authorized coordinate-to-Maps playbook passed again at `cases/compass-location-empty-maps-regression-20261015/`.

The denied state was then tested on both apps by temporarily selecting Never in Settings. Both hid coordinates, place and elevation. The initial clone kept its dial and heading text too high; after a layout correction and another TrollStore install, the [denied-state comparison](../cases/compass-location-denied-comparison-20261015/report.md) measured the original/clone center disk at rows 315–394/314–395 and heading text at 679–728/680–728 on the 414×896 XR screen. Its screenshots, pre-fix comparison, Settings evidence and hashes passed `copyapp verify`. Both apps' While Using permission was restored, with Precise Location still enabled. The verified original report is `cases/compass-xr-deep-report-v14-20261015/`. The screenshots establish visible behavior, while the static call chain remains an inference about which internal methods ran on that occasion.

## Automated report-to-rebuild handoff

The verified [Compass deep report v18](../cases/compass-xr-deep-report-v18-20261015/report.md) cites completed original playbooks for live heading, bearing lock and coordinate-to-Maps. [Rebuild plan v3](../cases/compass-rebuild-plan-v3-20261015/runbook.md) generated all three original/clone script pairs from those citations, with no missing source script. Copy Compass 0.1.3 (4), IPA SHA-256 `135af1d3ae96057a96da9c49fea95f8a4d71649df6fe9b408c1267e9b76bf72b`, was installed on the XR through TrollStore. The [three-flow XR comparison](../cases/compass-three-flow-rebuild-check-v4-20261015/report.md) completed and passed case-hash verification. The final launch, taps, screenshots and Apple Maps handoff were observed on both apps.

The first automated run exposed that repeated iOS MCP screenshots can leave Compass's accessibility text empty even while the image remains visible. The playbook runner now records a Mac Vision OCR result bound to the saved screenshot when accessibility checks fail; the resumed run completed. Comparison screenshots also exposed overlapping `140` and `150` labels in the clone's bearing-lock state. The clone now suppresses the nearest dial number while a locked bearing label occupies its position. Manual review of the final comparison confirms that overlap is gone. Red-marker brightness varied across stationary original runs, so the final bearing playbook retains screenshots for review without a color-pulse pass claim.

The final comparison's visual-check status is `unreviewed` for all three flows: there is no pixel-equivalence threshold or automatic semantic check for these dynamic screens. Screenshot review still shows changing status-bar/back-navigation labels and elevation values, plus an elevation line visible on the clone but absent in one original locked capture. The flow result proves selected interactions and the Maps foreground handoff, not complete screen or sensor fidelity. iOS 17 and 26 remain outside this XR trial.
