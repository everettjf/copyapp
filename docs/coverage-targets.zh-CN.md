# 如何设定动态复刻目标

[English](coverage-targets.md) · [简体中文](coverage-targets.zh-CN.md)

“完整复刻”应针对具体 App 和设备状态定义，不能默认承诺。简单 App 的功能边界可能足够清楚，可以把已知功能全部实现并验证；大型 App 的第一阶段可以只选择已知能力的 50–60%。分析后确定目标，交付时明确实际完成的范围和缺口。

## 1. 分析后建立能力清单

按用户可见的能力及关键状态盘点，不按类、页面或代码行数计数。例如，“创建本地笔记，重启后仍可搜索到”是一项能力；编辑器截图本身不是。视 App 情况纳入导航、持久化、权限、离线与网络行为、扩展、账号和支付等。把相关状态组成合理的功能项，避免把一项操作拆成很多容易通过的小项。每项关联观测证据，未观察到的状态要标明。清单只是**已知能力基线**，无法证明没有隐藏功能。

每项记录稳定 ID、描述与验收行为、证据依据、相对重要性权重（1–5）、可行性或依赖，以及 `selected`、`deferred` 或 `blocked`。另外列出未知功能领域。已知但困难的功能不能悄悄从分母删掉。

## 2. 选择阶段目标

选择能组成完整用户旅程的能力，记录选中的 ID、目标设备与原版构建、阶段时间或迭代，以及每项推迟或受阻的原因。先做核心路径和连续行为，再扩展装饰性页面。百分比用于描述范围，不能代替逐项验收。

沿用事先声明的权重：

`目标覆盖率 = 已选已知能力的权重 / 已知能力总权重`

“3/3 条测试流程通过”仅表示这三条选定流程 100% 通过，不能写成整个 App 的 100%。若能力清单尚不充分，先只声明**具名范围**，不要给整个 App 一个百分比，继续发现。大型 App 的 50–60% 只是可能商定的阶段目标，不是自动阈值或效果保证。简单 App 可以把已知清单的 100% 作为目标，但仍须披露未知状态及测试限制。

实现前固定清单和权重。新证据改变范围时，用 `--previous` 与 `revision_reason` 新建目标，保留原案例和修订案例。修订可以增加能力或调整范围，但不能删除、弱化已知能力或改变其权重。分析基线变化时应建立新的报告和目标。不能因为验证失败就降低目标来制造完成的印象。

`copyapp rebuild-plan --report <报告> --flow <ID> ... --out <计划>` 可以为一个实施任务选择 1–12 条已审阅流程。更大的阶段目标需要多个有界计划／任务／案例；`coverage-plan` 支持重复 `--plan`，`coverage-delivery` 支持重复 `--delivery` 汇总。一个完成的 `copyapp copy` 父案例不能证明大型 App 的全部能力。每项选定能力都应链接到对应任务和检查。

## 3. 先浅后深，再核算交付

先让选定用户旅程可运行，具备主要页面结构与核心操作；再补状态变化、持久化、权限、网络结果和视觉细节。每项在同一台设备、等价初始状态下对照原版和复刻版。只有声明的行为及视觉验收均通过，才标记 `verified`；否则标记 `partial`、`failed` 或 `untested`，附证据和原因。模拟的服务端结果必须写明 `simulated`，不能算作真实服务行为等价。

如果已知能力分母成立，交付时分别给出三个数字：

- **目标覆盖率：**已选权重 / 已知清单总权重。
- **阶段完成率：**已验证的已选权重 / 已选权重。
- **已知能力实证覆盖率：**已验证的已选权重 / 已知清单总权重。

例如已知十项同权重能力，选六项、五项通过，应报告目标 60%、阶段完成 5/6（83%）、已知能力实证覆盖 50%。同时列出一项未完成、四项延后、未知领域、重大视觉差异以及设备与构建限制。页面能显示或脚本成功退出都不足以把能力计为完成。

`copyapp coverage-plan` 现在会校验并固定人工提交的能力清单，绑定审阅报告与已选复刻计划。`coverage-delivery` 根据该清单与一个或多个通过校验的 `agent-delivery` 案例计算三个数字。审阅者仍须逐项判断结果并说明证据；若对应流程缺少通过的行为断言，或没有完成逐图审阅，或存在重大视觉差异，CLI 会拒绝把它标记为 `verified`。哈希与算术可机器校验；清单是否完整、权重是否合理、语义是否等价仍需人工审阅。单独的 `feature-spec.json` 和 `agent-delivery` 只是选定流程的证据，不能直接当作整个 App 的分数。

## CLI 输入与命令

审阅报告与复刻计划就绪后保存能力清单 JSON：

```json
{
  "schema_version": 1,
  "target_bundle_id": "com.example.original",
  "rebuilt_bundle_id": "com.example.clone",
  "rationale": "先实现本地创建和搜索",
  "unknowns": ["未观察到的服务端状态"],
  "capabilities": [
    {"id": "create", "name": "创建项目", "acceptance": "创建并显示本地项目", "basis": "审阅后的原版流程", "weight": 3, "scope": "selected", "flow_ids": ["create"]},
    {"id": "sync", "name": "账号同步", "acceptance": "跨设备同步", "basis": "可见账号入口，但未操作", "weight": 2, "scope": "blocked", "flow_ids": [], "reason": "没有测试账号"}
  ]
}
```

每条选定的复刻流程必须恰好归属一项选定能力；权重为 1–5 的整数。延后和受阻的已知能力仍计入分母，并须写明原因。验收描述应与关联流程的证据一致；单张截图不能证明持久化或服务端等价。

```sh
copyapp coverage-plan --report <报告案例> --plan <复刻计划案例> \
  --inventory <清单_JSON> --out <目标案例>
copyapp verify <目标案例>
```

修订同一报告基线时，在新清单添加 `revision_reason`，传入 `--previous <旧目标案例>`，并使用新的输出目录。真机 `agent-delivery` 完成后，为清单中每一项提交判断：

```json
{"schema_version": 1, "capabilities": [
  {"id": "create", "result": "verified", "notes": "成对行为通过；已记录轻微图标差异"},
  {"id": "sync", "result": "untested", "notes": "没有测试账号"}
]}
```

`result` 可以是 `verified`、`partial`、`failed` 或 `untested`；延后／受阻项必须保持 `untested`。随后执行：

```sh
copyapp coverage-delivery --plan <目标案例> --delivery <复刻交付案例> \
  --review <审阅_JSON> --out <覆盖交付案例>
copyapp verify <覆盖交付案例>
```

多个有界任务可重复使用 `--plan` 和 `--delivery`。只有全部选定权重通过验证时，阶段目标才算达成。结果报告逐项列出缺口和未知；即便阶段完成率为 100%，也只针对选定的已知能力。

## 案例记录模板

| ID | 能力与验收行为 | 证据 | 权重 | 范围 | 结果 | 差异／原因 |
| --- | --- | --- | ---: | --- | --- | --- |
| local-create | 创建本地项目，重启后仍存在 | 原版流程与本地数据观测 | 5 | selected | verified / partial / failed / untested | 写明具体差异 |
| account-sync | 跨设备同步账号项目 | unobserved | 5 | blocked | untested | 无账号或服务端访问条件 |

表格后记录已知清单总量、选定 ID、目标修订、合理情况下的三个覆盖数字、未知领域，以及原版／复刻版精确检查的链接。即使阶段中其他检查通过，最终面向用户的摘要也必须写明重大视觉缺口和未验证的后端行为。
