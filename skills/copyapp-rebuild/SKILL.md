# Rebuild from an analyzed app

For a verified `ios_behavior_report`, follow [standard mode](../../docs/ios-standard-mode.md) ([中文](../../docs/ios-standard-mode.zh-CN.md)) with `rebuild-plan`/`prepare-rebuild --backend ictrl`, a task pinned to the exact device, development signing and `install --transport usb`. `rebuild-task-check` infers standard execution from the feature specification. Use post-action AX/playbook assertions and full screenshot review; a Frida/UIKit `final_view` is not part of this UI-only contract. Keep coverage and bounded fidelity milestones, independent source/Bundle ID, and the install/check/visual-review/agent-delivery source bindings below. Historical enhanced installs and strict standalone parents retain their original rules; do not substitute ldid/TrollStore for ordinary development signing or mark a strict parent complete from a fidelity grade alone.

For agent-led development, follow [bounded fidelity](../../docs/fidelity.md): after
the verified `agent-task`, create `fidelity-plan --task <TASK_CASE> --out <CASE>`.
Default to grade 80/100 and three implementation/check cycles including the first;
honor explicit user settings. Work through the stages directly. Use an iOS
`agent-delivery` with full image review as `fidelity-check --evidence`, retain all
differences and stop at `target_met` or `iteration_limit`. At the limit deliver
current runnable artifacts and gaps as incomplete. Supported failed attempts count
too. The grade is not an image-similarity percentage or capability coverage. Existing
standalone parent/strict-delivery rules below keep their original meanings; a
bounded milestone does not make an incomplete strict parent pass.

Read the case report and `feature-spec.json`. Select the requested flows and carry their evidence IDs into the implementation and comparison notes. Preserve unknowns: a static method name or one screenshot does not specify all behavior or assets.

For a “complete rebuild” request, first set a documented milestone from the known-capability inventory using [coverage targets](../../docs/coverage-targets.md) ([中文](../../docs/coverage-targets.zh-CN.md)). A simple App may target all known capabilities; a complex App may deliberately target a smaller useful slice. Once the report and plan exist, run `copyapp coverage-plan`; after the runnable shallow pass, deeper selected behavior and real-device `agent-delivery`, run `copyapp coverage-delivery` with explicit reviewed decisions. Report target coverage, milestone completion and verified known coverage with the named denominator and limits. The CLI's selected-flow pass rate is not an App-wide percentage.

For a verified Copy APP deep report, run `copyapp rebuild-plan --report <REPORT_CASE> --out <PLAN_CASE>` before writing paired UI scripts by hand. It copies the reviewed feature spec, selects cited original playbooks, and creates clone playbook drafts by changing only the top-level Bundle ID. A final UIKit assertion can disambiguate cited original flows with different endings. Inspect `runbook.md` and `rebuild-plan.json`: `ready_for_implementation` means the scripts pass structural preflight, while `needs_original_playbook`, `ambiguous_playbooks`, and `no_matching_final_view` require more original evidence. Implement the selected UI and behavior in an independent app before executing the generated `rebuild-check` command; the plan does not build or validate the clone.

After the plan, run `copyapp agent-task --report <REPORT_CASE> --plan <PLAN_CASE> --udid <UDID> --project <SOURCE_DIR> --out <TASK_CASE>`. Read its `TASK.md` and `task.json` as the concrete implementation contract. This step rechecks report/plan hashes, each cited original script, the fact that the clone script only changes Bundle ID, and structural preflight; it links each flow to the copied UI, runtime and decompiler evidence. `ready_for_agent` means the selected scripts and evidence are available, not that code was generated or behavior passed. If it says `needs_evidence`, repair those flow gaps before claiming a full rebuild. Coding agents should then implement the independent source project, build it and iterate against the generated comparison command; the task file is a handoff, not a substitute for that work.
For one resumable handoff, `copyapp prepare-rebuild --report <REPORT_CASE> --udid <UDID> --project <SOURCE_DIR> --out <CASE>` generates both `plan/` and `task/TASK.md`. Repeat `--flow <FLOW_ID>` to select a subset, and add `--resume` after interruption; verified stages are reused and damaged stages are archived. Read its status before implementation.
After installing the rebuilt App, `copyapp rebuild-task-check --task <TASK_CASE> --out <REBUILD_CHECK_CASE>` uses the task's pinned device, source report, selected pairs and backend. It rechecks source scripts before replay; use `--udid` only when the task has no pinned device and `--resume` after interruption. The expanded `rebuild-check --pair ...` command remains available for manual pair selection.

If this skill is already running inside Codex or Claude Code, implement the task directly. For a standalone strict shell/automation entry, `copyapp agent-run --task <TASK_CASE> --provider codex|claude --verify-rebuild --out <RUN_CASE>` gives the installed coding-agent CLI fixed `install/`, `rebuild-check/` and `visual-review/` destinations. After exit it creates a source-linked `agent-delivery/` case; success requires behavior assertions for every selected flow, complete screenshot review and no major visual difference. Inspect that case and `rebuild-verification.json`; minor differences remain recorded. Use `--dry-run` to inspect the invocation first. `agent_exited_unverified` records process exit only, so a CLI exit is never itself proof of a working rebuilt App.

Once the independent project, IPA, install record and completed `rebuild-check` case exist, run `copyapp agent-delivery --task <TASK_CASE> --install <INSTALL_CASE>/install.json --check <REBUILD_CHECK_CASE> --out <DELIVERY_CASE>`. Pass `--run <RUN_CASE>` only if the source was actually produced through `agent-run`. Inspect `delivery.json` and `report.md`: a matched device/package and completed scripts establish execution; an explicit `final_view` or visual check establishes only its declared behavior; `unreviewed` visuals remain open. The delivery case rechecks its external task, source tree, IPA, installation and comparison hashes when verified. Do not report whole-App fidelity from a selected-flow delivery.
Operation-after-tap playbook assertions, including numeric deltas and visible content, also count as bounded behavior evidence when both original and rebuilt runs complete. For SwiftUI content that lacks a UIKit UILabel, retain these checks rather than treating the absence of `final_view` as missing behavior proof. Review every screenshot pair with `copyapp visual-review --check <REBUILD_CHECK_CASE> --judgments <JSON> --reviewer <NAME> --out <CASE>` and pass `--visual-review <CASE>` to `agent-delivery`; record different stored-data baselines as visible differences instead of silently normalizing them.

Implement with a separate bundle ID and independent code. Prefer public iOS APIs for sensor, location, navigation, and UI behavior. Set the deployment target for the selected devices and verify Xcode output before attempting installation. Do not copy credentials, private user data, Apple entitlements, or unlicensed third-party assets into the new app.

After each flow, install and **launch** on the real device, then compare the target and rebuilt app from equivalent states. Installation success alone is insufficient: check process launch, screen, interaction, state transitions, and relevant permission states. Save screenshots and action results with device/build identity. If signature or runtime errors occur, diagnose those before claiming the flow works.

For repeated UI flows, run paired `copyapp playbook` scripts on the same device and UI backend. Give both scripts the same `scenario_id`, action sequence and coordinate taps; set `stable: true` and `ready_contains` on screenshot steps so launch transitions are rejected. Use `copyapp compare-playbooks --original <CASE> --rebuilt <CASE> --out <COMPARISON>` to retain both evidence sets, aligned screenshots, differences and any declared visual state checks. Run `copyapp verify` on the comparison and inspect the images. A passed color signal or a low pixel difference covers only that declared region/state, not full feature parity. Preserve failed or premature capture cases as diagnostics.

For several selected flows from one `feature-spec.json`, use `copyapp rebuild-check --udid <UDID> --feature-spec <SPEC> --pair <FLOW_ID> <ORIGINAL_SCRIPT> <REBUILT_SCRIPT> ... --backend <BACKEND> --out <CASE>`. It rejects mismatched action labels, coordinates, initial observations, scenario IDs, or unstable screenshots before operating the phone. It records both installed App versions, runs each pair on one device, compares the saved screenshots, and rechecks versions after each flow. After a failure, repeat the same inputs with `--resume` to retain validated completed runs. Read the parent report and review each screenshot pair; `status=complete` with `checks_status=unreviewed` proves execution and evidence capture, not feature equivalence. Add a case-specific visual/behavior review with explicit observed values before reporting coverage.
For a repeatable numeric comparison of the saved screenshots, run `copyapp visual-audit --check <REBUILD_CHECK_CASE> --roi X1 Y1 X2 Y2 --max-mean <NORMALIZED_LIMIT> --max-changed <PIXEL_FRACTION_LIMIT> --out <AUDIT_CASE>`. The ROI must cover at least half the screenshot; the tool verifies each source hash and recomputes the metric on `copyapp verify`. Declare the ROI and thresholds before a new acceptance run when possible; thresholds chosen after viewing results are diagnostic. Inspect paired images and record specific differences separately. A metric result does not change a source comparison's `unreviewed` visual status or prove dynamic visual parity.

When a selected flow ends on a UIKit result label, add `final_view` to that flow in the feature spec with exact `text` and a bounded `region_points` display area. Add `also` entries with the same shape for other exact visible labels, such as C/AC button state; each needs its own tight region. To check dismissal of a dialog, add `absent` entries with exact text and a bounded region, such as `Cancel` in the former dialog area. `rebuild-check` captures the view tree immediately after each playbook without relaunch, requires one visible matching label for `final_view` and each `also` entry, and requires zero matching visible labels for each `absent` entry on both App variants. Keep the result region above keypad labels when checking a Calculator result. Verify the parent case and inspect the captured nodes, their ancestors, and the paired screenshot. These checks prove only the declared labels at that observation time; they do not establish intermediate values or support self-drawn/SwiftUI content by themselves.

For navigation into another app, add `expect_foreground` with the destination Bundle ID after the tap. Compare the same destination in both scripts; this checks the handoff, not any deep link parameter or final page content.

For the Compass bearing sector, `scripts/compass-heading-offset.py` captures locked, 45° offset and restored states on the XR, and `scripts/compare-compass-offset.py` compares the verified source cases. The original uses a temporary in-memory bearing-view angle change and the rebuild offsets the CoreMotion getter. Compare only the sector region because those injection points produce different whole-screen headings. Inspect the saved angle, radius, screenshot and restoration evidence before claiming a visual match.

For the Compass coordinate handoff, `scripts/compass-maps-url.py` records the actual `UIApplication` Maps URL and the settled Maps screen after a coordinate tap. Use `scripts/compare-compass-maps-url.py` on two verified source cases to check exact URL equality without printing device coordinates in the comparison report.

For the Compass pilot, the project is `examples/rebuild/CompassClone`; package it with `sh examples/rebuild/CompassClone/package.sh`. The XR's ordinary USB installation service accepted its temporary-signed IPA but SpringBoard rejected launch. On a paired jailbroken device with TrollStore, use `copyapp install --udid <UDID> --ipa <IPA> --out cases/<INSTALL_CASE>`; it verifies device identity, transferred SHA-256 and installed bundle/version. Then launch with `copyapp ui launch --bundle <BUNDLE_ID>` and observe the actual screen. This install command was tested with the known-source fixture on XR; the case report lists Compass's three pilot flows and remaining evidence gaps.
